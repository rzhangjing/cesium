# 以原版 CesiumJS Specs 为唯一事实来源进行 Rust 测试移植

_来源：17b6da4 → b77dd27 提交周期内记录的编码计划——内容为规划时意图，实现可能滞后或有出入。_

**状态：** accepted

## 背景
Rust 移植版仅覆盖原版 6.4% 的 Spec 用例（816/12,823），导致大量用户可见 bug（地球渲染、相机控制、瓦片 UV 映射、WebMercator）未被任何测试验证，"测试通过"不等于"功能正确"。

## 决策驱动
- 以原版行为作为验收标准
- 自动化回归替代手动验证
- 按依赖顺序分阶段推进

## 备选方案
- **基于原版 Specs 逐用例移植为 Rust #[test]** — 优点：每个函数都有机器可验证的正确性；失败即暴露实现偏差；覆盖率可量化
- **自行编写业务场景驱动测试** _（已否决）_ — 优点：贴近真实使用；缺点：无法保证覆盖原版所有边界与精度行为；难以衡量是否等价于 CesiumJS

## 决策
将原版 CesiumJS 的 `Spec.js` 作为 ground truth，逐个移植为 Rust `#[test]`，一一对应命名与语义；测试失败默认判定 Rust 实现有误并修复，仅在确认为平台差异时才记录显式偏差。

## 影响
建立 Phase 0→Phase 5 的分阶段路线图，维护覆盖率跟踪矩阵；A/B/C 三类模块分类处理，浏览器/DOM/网络相关（C 类）不硬移植而是标注不可移植原因；数学层委托 glam 但需额外验证 CesiumJS 特有包装函数的坐标转换语义。
