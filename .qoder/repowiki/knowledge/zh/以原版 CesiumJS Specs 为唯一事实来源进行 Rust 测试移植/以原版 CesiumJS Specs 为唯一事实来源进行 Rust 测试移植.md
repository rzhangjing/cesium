# 以原版 CesiumJS Specs 为唯一事实来源进行 Rust 测试移植

_来源：5a0e37f → aff355e 提交周期内记录的编码计划——内容为规划时意图，实现可能滞后或有出入。_

**状态：** accepted

## 背景
现有 816 个 Rust 测试全部通过，但仅覆盖原版 CesiumJS 的 6.4%（57/600 Spec 文件），用户暴露的地球渲染、相机控制、瓦片 UV 映射等 bug 恰好落在未覆盖区域。

## 决策驱动
- 以原版行为为验收标准
- 自动化回归替代手动验证
- 按依赖顺序分阶段推进

## 备选方案
- **直接编写新测试** _（已否决）_ — 优点：灵活；缺点：缺乏权威基准，无法保证与原行为一致
- **基于原版 Spec.js 逐用例移植为 #[test]** — 优点：每个断言都有可追溯的原版输入/期望；失败即默认实现有误；覆盖率可量化；缺点：工作量大（约 7,000+ A/B 类用例）；需处理平台差异

## 决策
将原版 CesiumJS 的 ~12,823 个 Spec 用例系统移植为 Rust `#[test]`，并以原版行为作为 ground truth：测试失败默认判定 Rust 实现错误并修复，仅在确认为 f32/f64、浏览器 API 缺失等平台差异时才记录显式偏差。

## 影响
建立 Phase 0→Phase 5 的分阶段路线图与覆盖率跟踪矩阵；A 类纯逻辑必须 100% 移植，B 类仅验证 glam 之上的 CesiumJS 特有包装，C 类（Renderer/WebGL/DOM/网络）标注不可移植原因不计入覆盖率；每个模块验收需满足 A 类 100% 通过、发现的 bug 全部修复并附回归测试。
